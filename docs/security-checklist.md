# Чек-лист безопасности

Этот чек-лист основан на анализе документации проекта и содержит пункты, которые следует проверить для обеспечения безопасности.

## 1. Аутентификация и Авторизация

*   [ ] **Управление сессиями:**
    *   [ ] JWT-токен имеет срок действия 7 дней, отзыв сессий невозможен без смены `JWT_SECRET_KEY`.
    *   [ ] Ссылка `/web` для входа в веб-панель одноразовая (5 минут), но JWT можно использовать сколько угодно раз в течение этого времени. Необходимо хранить `jti` использованных токенов.
*   [ ] **Защита от перебора паролей:**
    *   [ ] Нет ограничения попыток на `POST /api/login` для `ADMIN_USERNAME`/`ADMIN_PASSWORD`.
*   [ ] **Доступ к данным:**
    *   [ ] Роли `admin`/`user` реализованы.
    *   [ ] Изоляция данных через `user_id` для большинства таблиц.
    *   [ ] `admin` имеет доступ к данным других пользователей (`?target_user_id`, `?all_users=true`).
    *   [ ] Пользователь `user` с чужим `target_user_id` получает 403, обращение к чужой записи по id — 404.
    *   [ ] Справочник категорий (`categories`) общий для всех.
*   [ ] **Аутентификация бота:**
    *   [ ] Middleware находит пользователя по `telegram_id`; незарегистрированным отвечает отказом.

## 2. Целостность данных

*   [ ] **Дубликаты записей:**
    *   [ ] Нет уникального индекса `assets(user_id, ticker)` — возможны дубли.
    *   [ ] Дубли транзакций отсекаются в Python (по дате+сумме+банку+40 символам описания), но нет ограничения на уровне БД.
*   [ ] **Валидация:**
    *   [ ] Нет ограничения размера загружаемого файла на `/api/upload`.
*   [ ] **Консистентность:**
    *   [ ] `GET /api/dashboard-stats` вызывает `seed_default_categories` на каждый запрос.

## 3. Уязвимости (XSS, инъекции)

*   [ ] **XSS:**
    *   [ ] Часть данных вставляется через `innerHTML` без экранирования в `reminders.html`, `index.html`, `upload.html`.
    *   [ ] Необходимо применить экранирование (`escapeHtml()`) везде.
*   [ ] **Напоминания:**
    *   [ ] Текст напоминаний с `<` или `&` при `parse_mode="HTML"` без экранирования приводит к ошибкам Telegram и бесконечному повторению отправки.
    *   [ ] После N неудачных попыток помечать напоминание и логировать.
*   [ ] **SQL-инъекции:**
    *   [ ] Используется SQLAlchemy 2 с `asyncpg`, что обычно безопасно при правильном использовании ORM.
    *   [ ] Необходимо убедиться, что все строковые параметры в запросах правильно обрабатываются ORM.

## 4. Инфраструктура и Развертывание

*   [ ] **Docker:**
    *   [ ] Нет `.dockerignore` → в образ попадают `.env` (секреты), `.git`, старый код.
    *   [ ] В проде используется `volumes: - .:/app`, код берётся с хоста (для разработки нормально, для прода — нет).
    *   [ ] Контейнер работает от root (небезопасно).
    *   [ ] Нет `HEALTHCHECK` для `app` (исправлено в `deployment.md`, но проверить).
*   [ ] **Бэкапы:**
    *   [ ] Настроен ежедневный `pg_dump` с ротацией (`backup` сервис).
    *   [ ] Каталог `./backups` лежит в том же LXC, что и база (нет защиты от смерти диска).
    *   [ ] **Необходимо настроить копирование дампов вне LXC** (NAS, облако).
*   [ ] **Доступ извне:**
    *   [ ] Порт 8000 может быть проброшен в интернет.
    *   [ ] Рекомендуется доступ только через VPN (WireGuard/Tailscale).
*   [ ] **Конфигурация:**
    *   [ ] Секреты (токены, пароли, ключи) хранятся в `.env`.
    *   [ ] `FATSECRET_CONSUMER_KEY/SECRET` и токены FatSecret хранятся в БД в открытом виде (допустимо для домашнего сервиса, но стоит знать).
    *   [ ] `datetime.now()` без таймзоны (работает, т.к. контейнер в UTC, но не является лучшей практикой).
    *   [ ] Даты фильтра дашборда трактуются как UTC, а не как местное время.

## 5. Устаревший код и зависимости

*   [ ] **Устаревший код:**
    *   [ ] В репозитории есть старые копии кода (`bot/`, `services/`, `web/` и т.д.), которые не используются (`app/` — актуальная версия).
    *   [ ] Необходимо удалить эти устаревшие файлы/каталоги.
*   [ ] **Зависимости:**
    *   [ ] Версии библиотек закреплены в `requirements.txt`, но для продакшена может потребоваться lock-файл (`pip-compile`/`uv`).
*   [ ] **CI/CD:**
    *   [ ] `.github/workflows/ci.yml` настроен (ruff + pytest + сборка Docker-образа).
    *   [ ] Тесты покрывают только unit-кейсы, нет тестов API (FastAPI `TestClient`).
    *   [ ] Тест цепочки миграций хардкодит голову — нужно править при каждой миграции.

## 6. Прочее

*   [ ] **Bot FSM:** Состояния диалогов хранятся в памяти — теряются при рестарте (можно `RedisStorage` или хранить в Postgres).
*   [ ] **Интеграции:**
    *   [ ] MOEX запрашивается при каждом открытии дашборда — нужен кеш.
*   [ ] **Разделение процессов:**
    *   [ ] Весь процесс — один (`asyncio.gather`). Нельзя запустить несколько воркеров uvicorn, задачи планировщика и бота задублируются.
    *   [ ] Падение одной части роняет всё.
    *   [ ] Необходимо рассмотреть разделение на `api` и `worker` или защиту планировщика от двойного запуска.
