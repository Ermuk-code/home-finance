# Внешние интеграции

## Home Assistant → вес

Умные весы передают замер в Home Assistant, автоматизация HA вызывает `rest_command`, который шлёт вес в Life OS.

1. В `.env`: `HEALTH_WEBHOOK_TOKEN=<результат openssl rand -hex 32>`, `APP_BIND_IP=<IP LXC или 0.0.0.0>`.
2. В HA `secrets.yaml`: `life_os_webhook_token: "<тот же токен>"`.
3. Добавить [`homeassistant/rest_command.yaml`](../homeassistant/rest_command.yaml) (заменить `<IP_КОНТЕЙНЕРА>`).
4. В автоматизацию весов добавить вызов из [`homeassistant/automation_snippet.yaml`](../homeassistant/automation_snippet.yaml):
   `profile` — кто взвесился (`admin`, `user`, имя, id или telegram_id), `weight` — вес в кг.

```
POST /api/health/webhook/weight
X-Webhook-Token: <HEALTH_WEBHOOK_TOKEN>
Content-Type: application/json

{"profile_alias": "admin", "weight_kg": 82.4, "bmi": 24.1}
```

Ответ `200 {"status":"ok","notified":true,...}`. Владелец замера получает пуш с разницей к прошлому замеру.

## Home Assistant → активность Android + iOS

### Подготовка телефонов

1. **Android + Amazfit/Zepp:** включить запись шагов Zepp в Health Connect и убедиться,
   что сегодняшние данные часов появились именно в Health Connect. В HA Companion:
   «Настройки → Приложение Companion → Управление датчиками → Health Connect» —
   включить **Daily Steps** (`health_connect_daily_steps`), разрешить чтение шагов и фоновый доступ,
   если он предлагается системой. Обычный Android `sensor.steps` считает шаги с перезагрузки
   и использует датчик телефона; он не заменяет дневные шаги часов.
2. **iPhone + Xiaomi/Mi Fitness:** включить запись шагов в Apple Health в Mi Fitness,
   проверить источник Mi Fitness в «Здоровье → Шаги → Источники данных».
   В HA Companion: «Настройки → Приложение Companion → Датчики → Apple Health Sensors» —
   включить **Steps** (`health_steps`) и при наличии **Active Energy** (`active_energy`),
   выдать разрешения на чтение. Если группы Apple Health нет, обновить Companion.
   Pedometer Steps использует процессор движения iPhone и не гарантирует импорт данных часов.
3. После синхронизации открыть в HA «Инструменты разработчика → Состояния», найти реальные
   entity_id обоих телефонов, сравнить дневные значения с Health Connect / «Здоровье».
   Фоновое обновление зависит от ОС, разрешений и доступности HA; расписание на сервере
   отправляет последнее полученное значение, а не принудительно опрашивает часы.

Названия и поведение сенсоров сверены с [официальной документацией Companion](https://companion.home-assistant.io/docs/core/sensors/).
`health_connect_active_calories_burned` описан как последняя оценка, а
`health_connect_total_calories_burned` включает базовый обмен. Нельзя выдавать их за суточные
активные ккал. Для `sensor.cph2719_total_calories_burned` в шаблоне указан
`calories_type: total`: REST-команда передаёт `total_calories`, а не `active_calories`.
Этот итог содержит базовый обмен и показывается как расход без дополнительных слагаемых.
Для iOS Active Energy оставьте `calories_type: active`. Если источник неизвестен, оставьте
`calories_entity: ""`; неизвестный общий расход не передаётся как нулевой.

### Сервер и Home Assistant

1. В `.env`: задать `HEALTH_WEBHOOK_TOKEN`, `APP_BIND_IP` (LAN-адрес), `ACTIVITY_TZ=Europe/Moscow`.
   Часовые пояса HA и телефонов должны совпадать с `ACTIVITY_TZ`.
   Для напоминаний: `ACTIVITY_NUDGE_ENABLED=true`, `ACTIVITY_NUDGE_STEPS=5000`.
   После изменения `.env` пересоздать приложение: `docker compose up -d --build`.
2. В HA `secrets.yaml`: `life_os_webhook_token: "<HEALTH_WEBHOOK_TOKEN>"`.
3. Объединить `rest_command` из [`rest_command.yaml`](../homeassistant/rest_command.yaml)
   с существующим разделом в `configuration.yaml`; не создавать второй одноимённый раздел.
   У активности указан адрес `192.168.1.22:8000` из ТЗ — заменить, если адрес сервера другой.
   При подключении через `rest_command: !include …` включаемый файл должен содержать только команды,
   без внешнего `rest_command:`; исходный файл можно использовать целиком как HA package.
4. Добавить элемент из [`activity_automation.yaml`](../homeassistant/activity_automation.yaml)
   в `automations.yaml`, заменить `steps_entity` и `calories_entity`. Для отсутствующих калорий — `""`.
   Проверить конфигурацию HA и перезагрузить REST-команды / автоматизации (либо перезапустить HA).
5. Автоматизация запускается каждые 2 часа, в 19:55 (перед напоминанием) и в 23:50.
   `unknown`, `unavailable`, отрицательные шаги и сенсор без отчета за текущую дату пропускаются,
   а не превращаются в 0 шагов. Используется `last_reported` современного HA.
   В 00:00 отправки нет, чтобы вчерашнее значение не попало в новый день.
   Значения активных ккал без свежего корректного сенсора передаются как 0;
   неизвестные общие ккал пропускаются.
   Если телефон целый день недоступен, его запись не создаётся.

### Контракт и проверка

```http
POST /api/health/webhook/activity
X-Webhook-Token: <HEALTH_WEBHOOK_TOKEN>
Content-Type: application/json

{"profile_alias":"admin","steps":3200,"active_calories":100}
```

Для Android с общим расходом вместо `active_calories` используйте:

```json
{"profile_alias":"admin","steps":6202,"total_calories":1850.72}
```

Миграция `a1f4c8d2e690` добавляет отдельную nullable-колонку `total_calories`.
Обновите **и REST-команду, и автоматизацию** из `homeassistant/`; одной замены датчика
недостаточно. В ручном вызове команды передавайте `calories_type: total`.
Без типа команда сохраняет прежнее поведение `active` для совместимости.
API принимает оба показателя, если есть два независимых источника; общий расход имеет
приоритет в аналитике, BMR и TEF к нему не добавляются. Дробные общие ккал сохраняются
до сотых. До конца суток это накопленный итог, а не прогноз полного дня.

`profile_alias` разрешается как у веса: роль, имя, id / telegram_id. При нескольких пользователях
одной роли нужно уникальное имя или идентификатор. Шаги и активные ккал — неотрицательные целые;
калории необязательны (0). Сервер определяет дату **при получении** по `ACTIVITY_TZ`, поэтому
не пересылайте вчерашние данные после полуночи и не настраивайте отложенный повтор через границу дня.
Атомарный PostgreSQL `ON CONFLICT (user_id,date) DO UPDATE` сохраняет максимум каждого счетчика:
повтор/запоздавшее меньшее значение не уменьшит итог; счетчики не суммируются.
Если требуется исправить ошибочно завышенное показание, этот вебхук его не понизит.
Общие ккал используют свой отдельный максимум и не стираются запросом без этого поля.
История до переключения формата не переклассифицируется автоматически: по старому JSON
нельзя узнать, какой источник использовался. Такие записи нужно исправлять отдельно после проверки.

1. В HA вручную вызвать `rest_command.send_activity_to_life_os` для `profile: admin`,
   `steps: 3200`, `calories: 100`; повторить с 4500 шагов. Проверить HTTP 200 и один `id` в ответах.
   Аналогично проверить `profile: user`. Для проверки без искусственных цифр запустить автоматизацию вручную.
2. Проверить `/api/health/activity`, карточку «Активность за сегодня» на дашборде и `/activity` в боте
   под каждым профилем. Обычный пользователь видит только свои данные. 0 ккал может означать отсутствие источника.
3. В 20:00 по `ACTIVITY_TZ` при включенном флаге пользователи с сегодняшней записью ниже порога
   получают личное предложение прогулки. Нет записи за сегодня — нет пуша; отсутствие связи не считается нулем шагов.
   Задача запускается раз в день, пропущенный запуск догоняется не позднее чем через 30 минут.
4. Для проверки уникальности в БД:

   ```sql
   SELECT user_id, date, count(*) FROM activity_logs
   GROUP BY user_id, date HAVING count(*) > 1;
   ```

   Запрос должен вернуть 0 строк. Таблица и уникальный индекс созданы существующей миграцией
   `7c1d2e9f4a60`; дополнительная миграция для этого этапа не требуется.

Появление сенсоров и реальную доставку из HA нужно подтвердить на обоих телефонах и вашем HA.
Автотесты проекта проверяют вебхук, сохранение и повторы, разграничение доступа, бота и расписание;
они не заменяют эту проверку устройств.

## FatSecret → питание

FatSecret отдаёт дневник питания только по **OAuth 1.0a** (3-legged). Токены пользователя бессрочные.

1. Создать приложение на platform.fatsecret.com, взять Consumer Key / Shared Secret (OAuth 1.0) → `.env`.
2. `WEB_BASE_URL` должен открываться в браузере телефона/ПК, на котором нажимают «Разрешить»
   (в LAN это работает, пока вы дома; снаружи — только через VPN).
3. В боте: `/link_fatsecret` → ссылка → войти в FatSecret → «Разрешить» → callback сохраняет токены в `users`.
4. Синхронизация: 07/11/15/19:00 и 23:50 (с пушем итогов), плюс по `/nutrition`.

Ожидающие привязки (request token) хранятся в памяти процесса 15 минут — после рестарта ссылку нужно запросить заново.

## MOEX ISS → котировки и купоны

Публичный API `https://iss.moex.com/iss` без ключа. Используется для текущих цен, купонов, дат погашения,
доходности облигаций и дивидендов. Запросы выполняются при каждом открытии дашборда / `/portfolio`
(таймаут 10 с, кеширования нет). Если MOEX недоступен, позиции показываются без текущей цены.

## Telegram

Long polling к `api.telegram.org`. Нужен только исходящий доступ в интернет из LXC.
